## Что решает этот навык

Когда ИИ-агентов (Claude Code, Cursor, Windsurf, Antigravity и др.) просят обновить CHANGELOG.md, они обычно по умолчанию обращаются к истории коммитов git и просто переписывают сообщения коммитов.

В итоге список изменений превращается в черновик разработчика:
- Мелкие и мусорные коммиты: `fix typo`, `wip`, `format with prettier`, `fix tests`.
- Промежуточные состояния: функциональность, добавленная в коммите A, переделанная в коммите B и отрефакторенная в коммите C, превращается в три несвязные записи.
- Внутренние изменения, невидимые пользователю: рефакторинг кода, вынос общих функций и переименование файлов, о которых пользователь и интеграторы не могут узнать.
- Правки невыпущенных функций, ошибочно принятые за изменения: доработка функциональности, которая ещё не была опубликована, ошибочно оформляется новыми пунктами `Fixed` или `Changed`, сбивая читателей с толку.

## Ключевые принципы

> Напоминаем: список изменений — это перечень существенных изменений для пользователей и разработчиков, а не хроника коммитов git. В эпоху ИИ этому следует уделить особое внимание.

### Изменения с точки зрения пользователя — единственная основа для записей

Каждая запись отвечает только на один вопрос: «Что заметит пользователь или разработчик в сравнении с предыдущим стабильным выпуском?» Если ответ «ничего», запись не создаётся.

### Отличие от git log

Все записи формируются исключительно на основе чистой разницы относительно предыдущего выпуска (например, `git diff <last-tag>..HEAD`) и исходного намерения. Команда `git log` полезна лишь для проверки того, какие файлы были изменены, но не может служить источником формулировок для списка изменений.

## Принципы отбора

| Исключить | Обязательно сохранить |
| :--- | :--- |
| Рефакторинг, вынос вспомогательных методов, переименования, перемещение файлов | Поведение, непосредственно заметное пользователю или разработчику |
| Правки типов, линтера, форматирования, комментариев | Новые или удалённые команды, параметры, страницы, скрипты, настройки |
| Внутренние изменения сборки и dev-сервера | Изменение значений по умолчанию или ограничений системы |
| Журналы решений, документация, внутренние файлы отслеживания | Устаревания, удаление и критические изменения (указывать обязательно) |
| Доработка ещё не выпущенного функционала (объединять с исходным пунктом) | Исправление ошибки в уже выпущенном коде, с которой пользователь мог столкнуться |
| Ошибка, появившаяся и исправленная внутри одного цикла выпуска | Принципиально новый контент или возможности |

## Чек-лист перед сохранением

Перед сохранением записей проверьте:
1. Каждая запись подтверждается наблюдаемым изменением в чистой разнице кода, с обязательным указанием конкретного изменения.
2. Отсутствуют описания несуществующих функций; каждое утверждение отражает фактически реализованное поведение.
3. Если функциональность подвергалась переработке, запись обновлена по месту в исходном пункте, чтобы исключить дублирование.
4. Если объединить (squash) промежуточные коммиты, все промежуточные и не соответствующие итоговому состоянию записи должны быть удалены.
5. Стиль изложения простой и прямой, без лишних описаний и пустых похвал («улучшено», «плавнее»).
